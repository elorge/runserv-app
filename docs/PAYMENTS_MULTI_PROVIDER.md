# Multi-provider payments & MTN MoMo (implementation notes)

Implements phases 0–4 (backend) and part of 3 (Admin) of *Runserv Multi-Provider Payments and MTN MoMo Implementation Recommendation*.

**Reused, not duplicated:** `Payment` is the payment attempt; `LedgerEntry`, `ActivityLog` (audit), `paymentSplit`, `claim()` compare-and-set pattern.
**Schema (additive, push as initial):** `PaymentProviderConfig`, `ProviderChangeRequest`, `PaymentEvent` (append-only, trigger in `post_migrate.sql`), `PaymentException`, `ReconciliationRun`; `Payment` gains `idempotencyKey`, `providerStatus`, `verifiedAmount/Currency`, `settledAt`; `PaymentStatus` gains CANCELLED, EXPIRED, REFUND_PENDING, PARTIALLY_REFUNDED, REVIEW_REQUIRED. After `prisma db push`/migrate, run `prisma/sql/post_migrate.sql`.
**Backend:** `src/services/payments/*` (secretBox, providerConfig, collection, reconciliation, adapters/mtnMomo), `routes/adminPayments.routes.js`, MoMo routes in `payment.routes.js`.
**Activation:** MTN MoMo is OFF unless an Admin enables it AND: row for the backend's environment, (LIVE ⇒ PRODUCTION_APPROVED + second Super Admin), credentials present, currency/service/limits declared. Customers only see it via `extraMethods` from `/payment config` when eligible. Paystack/Flutterwave/Orange are unchanged; a disabled config row is a kill switch.
**Safety:** idempotency key per user; amount taken from the booking, not the client; callback is never trusted (URL HMAC + server-side status read-back); amount/currency/reference must match or the payment goes to REVIEW_REQUIRED + exceptions queue; compare-and-set transitions.

## Update 2 — pending engineering work (20 Nov 2026)
- **Sweeper scheduler:** `services/payments/sweeper.job.js`, started from `server.js` (every 5 min; `PAYMENT_SWEEPER_ENABLED=false` / `PAYMENT_SWEEPER_INTERVAL_MS` to control). In-process lock; transitions are idempotent so multiple instances are safe.
- **Admin search/status:** `GET /admin/payments` search now matches provider reference. PaymentList/PaymentDetails show REVIEW_REQUIRED, CANCELLED, EXPIRED, REFUND_PENDING, PARTIALLY_REFUNDED, the MTN MoMo gateway, provider reference, verified amount and settled time.
- **Admin UI (Payments → Payment providers):** tabs Providers / Exceptions / Reconciliation / Audit log; provider settings editor (onboarding status, currencies, services, limits); write-only credential entry/rotation; per-payment event timeline; REVIEW_REQUIRED resolve dialog (mandatory evidence note); statement CSV upload for reconciliation; "re-check pending now". Type-checks and builds (`npm run build`).
- **Mobile building blocks (not yet in the booking flow):** `paymentAPI.initializeMomo/verifyMomo`, `services/momoPayment.js` (idempotency key + polling), `components/MomoPayModal.js`, `extraMethods` exposed from `CountryConfigContext`. `PaymentSelector` deliberately does NOT offer MoMo yet — see below.
- **Tests:** `tests/paymentOps.test.js` (32 tests): sweeper, reconciliation, RBAC over HTTP for every admin route, secrets absent from responses/audit/storage, MoMo webhook and initialize at route level. Full backend suite: 56 suites / 948 tests passing.
- **MoMo in the booking flow (pay after booking):** `PaymentSelector` shows MTN MoMo only when the backend lists it in `extraMethods`. The ride/delivery is booked as CASH; once it exists, `MomoPayModal` collects the MTN number and runs the prompt. Trip completion already honours a COMPLETED prepaid payment, so no double collection. Mobile code is syntax-checked only — test on a device with the sandbox.
